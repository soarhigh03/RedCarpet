# Airfield Defense Sandbox

A browser sandbox for one question: given where you put your sentry drones and what their radar can reach, does a wave of ramming drones get through? Everything else — the fictional air base, the flight model, the scene editor — exists to serve that run.

## Run locally

Use Node.js 22. Run `npm ci`, then `npm run dev`. Production output is generated by `npm run build`; `npm run preview` serves it locally. Open the printed localhost address; opening index.html as a file does not load the worker or models correctly.

## Deploy with GitHub and Vercel

1. Put this folder's contents in your GitHub repository, including `public/`, `src/`, `package.json`, `package-lock.json`, and `vercel.json`. The optimized GLBs and texture must be committed along with the code.
2. Import that repository into Vercel. If the repository contains only this app, leave Root Directory at the repository root. If this folder is inside a larger repository, select the app folder containing `package.json` as Root Directory.
3. Select the Vite framework preset. The included configuration uses `npm ci`, `npm run build`, and output directory `dist`. No environment variables or backend services are required.
4. Deploy. Vercel's Git integration will build subsequent pushes. The original Sites sign-in gate does not transfer to Vercel; configure Vercel's access settings for the audience you want.

Browser saves belong to each site origin. Export a scenario or recording from the old site, then import it on the Vercel site to transfer your work. The optional `.openai/hosting.json` in the original working checkout belongs to the earlier Sites deployment and is not needed by Vercel.

## Scene appearance

The workspace, timeline, inspectors, dialogs, analysis view, and hardware report share a dark simulation-console theme. The **Render mode** control below the scene switches between **Realistic** (the supplied models and their original textures) and **Holographic** (translucent cyan faces with height gradients, bright contours, a subtle coordinate grid, and a soft glow). Holographic is the initial default; the selection is remembered on this browser.

Changing appearance does not restart, step, or modify a simulation. Cameras, selected entities, routes, weather, and replay work in both modes. Appearance is a browser display preference, separate from scenario files and recorded results. The fictional reference image is shown only in Realistic mode when its reference toggle is enabled; Holographic shows the editable scene geometry above a grid. It does not infer geometry from the pixels of the image. Original material and texture references are restored when switching back, including shared and instanced GLB assets. Older saved Wireframe preferences open in Holographic mode.

## Supplied 3D assets

The jet uses the supplied Meshy military-plane GLB, and each tree grove mixes both supplied Meshy tree models. Browser copies are in `public/models/`, with lower-detail tree meshes for distant views. Trees share geometry and materials and are drawn in instances. All mesh textures and the Draco decoder are served from this project; no external model service is needed. The source files in Downloads are untouched.

A grove stands as many trees as its footprint holds, so a large woodland fills out instead of scattering a dozen trees, and the layout is repeatable on every load. Each grove carries three levels of detail: the supplied meshes up close, the lower-detail copies from about 340 m, and a generated canopy of a few triangles beyond about 1.1 km. The supplied models cost 11,000 to 35,000 triangles each, so the far level is what lets thousands of trees stand around a field without a frame-rate cost; at the default camera a 4,700-tree woodland draws in 174 instanced calls.

Hostile fixed-wing drones use the supplied `Meshy_AI_drone_1010190247_texture.glb`, presented as a Shahed-style model. This applies to existing, imported, and newly added hostile fixed-wing vehicles. Friendly drones retain their own appearance. The artwork changes the visual model only; routes, battery curves, flight settings, and scripted outcomes remain fictional and editable. The optimized browser copy is `public/models/hostile-drone.glb`.

The supplied grass image is tiled on the ground plane. Runways, taxiways, aprons, and roads remain paved surfaces above it, including after map edits. Use **Follow** on an aircraft or a tree grove for a closer view, or orbit and zoom with the mouse.

The GLBs have no animation clips or separate rigged mechanisms. The simulation moves and pitches the whole jet mesh through its takeoff and climb. Landing gear and control surfaces are part of the static supplied geometry. Display scale is for readability, not a claim about the real aircraft's dimensions.

## Covering screen and hard kill

The point of the sandbox is where sentries stand and what gets through, not building scenery. The tactical air base scenario ships a fleet of twenty sentry drones and a guided wave of ramming drones to run at it.

**Before a departure the fleet rotates.** Press play and most of it is not on station: eight drones fly a patrol ring and twelve sit on pods taking charge. Twenty-five seconds before the first roll they all leave the rotation and take station. Nothing recharges once it is up — the pods are where endurance comes back.

The split is not arbitrary. Closing a patrol ring is a ratio, not a radius: a drone crossing a ring of radius *r* at *w* takes *r/w* to reach the middle, and *n* patrollers at *v* revisit a bearing every *2πr/(v·n)*. Set one against the other and *r* cancels, leaving **n ≥ 2πw/v** — eight, for a 40 m/s run-in against a 35 m/s patroller, at any radius you choose. Radius only buys warning, so 300 m is picked for the 7.5 s it gives; the lap is 54 s and a bearing comes round every 6.7 s. Eight airborne is also exactly what the batteries allow: a 40 minute pack against a 60 minute charge sustains 40% of a fleet in the air, so eight flying wants twenty on strength.

| | |
| --- | --- |
| Patrol ring | 300 m radius, 70 m altitude |
| Lap | 54 s at 35 m/s |
| Revisit at any bearing | 6.7 s |
| Drones to close the ring | 8 — `n ≥ 2πw/v`, independent of radius |
| Sustainable airborne fraction | 40% (40 min pack, 60 min charge) |
| Fleet | 20: eight on the ring, twelve on pods |

**What a sentry can see** defaults to the published TI AWR2944P EVM figures: 76–81 GHz, 4TX/4RX, azimuth 6 dB beamwidth about ±45°, elevation 6 dB about ±5°, and 200 m taken as the working range on a small drone. Range is not a published number for this part — it depends entirely on configuration and target — so it is the one figure here chosen rather than quoted. `URAD_INDUSTRIAL_V2` is kept alongside it in `src/defence.ts` if you want to compare a short-range wide-field module; swapping the sentry sensor is one constant.

The elevation beam is what shapes the layout. ±5° is ±17 m of height at 200 m and ±9 m at 100 m, so the sensor sees a thin horizontal slab rather than a dome: a drone descending on the runway crosses it instead of sitting in it. That is why the posts are stacked in five altitude layers from 15 m to 115 m rather than spread along the ground.

**Speed decides how much of that range is usable.** 200 m of warning against a 40 m/s run-in is five seconds, and five seconds is only worth what the airframe can cross in it. At 35 m/s and about 1.5 g that is a 134 m dash, so two posts a layer cover the 500 m a departure is vulnerable over. At the 15.6 m/s of a survey quad the same five seconds buys 58 m and the same job needs three times the drones — the radar is rarely the thing to spend money on first.

**The engagement is decided by each drone on its own.** There is no shared picture. Every step a sentry reads its own radar, classifies what it holds, and if it holds a hostile track *and is the closest of the sentries that also hold it that can actually make the crossing*, it works out where that track crosses it — the foot of the perpendicular from itself onto the line the target is flying — and checks it can get there before the target does. When the target is passing directly overhead or underneath, that dash is straight up or down. It then waits on the track and the takedown resolves on contact, swept over the step rather than sampled at its end.

**The attackers are guided.** Each one steers at the departing aircraft every step, leading it by the time it takes to close and limited to a 3 g turn. This is not decoration: a precomputed route cannot chase a target accelerating from 85 to 250 m/s, and an open-loop path drifts metres within seconds from the acceleration ramp, climb clamps, waypoint corner-cutting and wind alone. Guidance has to live inside the step.

That changes the problem completely. Against a fixed aim point the screen was most of the answer; against a guided threat chasing an F-35, the aircraft outruns almost everything. The shipped wave is two drones at about 50 m/s, timed to converge on the roll; across eight rolls the screen holds eleven of sixteen. Adding posts past about twelve stops changing the number — what binds is no longer coverage or count but the few seconds of the roll during which a 40 m/s drone can reach an aircraft at all.

**Rolling an attack.** The **Threat** panel holds the wave recipe: how many, how fast, how high, how far out they are released, how wide the window is, and the strike time the wave is timed to converge on. Release is worked back from each drone's run-in, so a wave arrives when the aircraft is moving rather than at an empty runway. The same plan and seed always produce the same wave, so you can move a sentry and replay the identical attack.

The scoreboard over the view tracks inbound, holding, tracked, engaging, stopped and leaked, and shows the ring-and-pods split until the screen forms up.

## Use the workspace

The window belongs to the 3D view. Panels float over it and each one collapses: **Forces** and **Threat** on the left, the **Inspector** on the right, transport and log along the bottom. Collapse states are remembered on this browser.

The header switches between **Simulate** and **Map setup**. Simulate is the tactical view — forces, threat rolls, the engagement. Map setup is where scene building lives: the object list, the add-object palette, weather, and the image-to-3D editor. Adding an object switches you there; adding a vehicle switches you back.

1. Open **Scenarios** to select one of six examples. The performance example includes fifty drones and three aircraft over ten simulated minutes.
2. Select a vehicle or map object in the scene explorer. Edit the inspector and choose **Apply changes**. A sentry gains two extra sections: its covering station and boresight, and its radar envelope. Map objects can also be moved with the 3D translation handles. Edits reset the current run and are undoable.
3. Vehicles have an ordered waypoint route. Coordinates use metres with X east, Y up, and negative Z north. **Add waypoints on map** appends points at 150 m altitude. All routes and altitude values can be edited numerically. Scenes with more than twelve vehicles show the selected route and avoid overlapping labels.
4. **Add event** creates an authored timeline outcome, which still works alongside the live engagement. Launch and delay events require a waiting vehicle. Stop, expend, and continue require active participants. A supporting participant, when supplied, must be active. Conflicting events are skipped with a reason in the flight log. Events at the same time are ordered by event ID.
5. Press Play, pause, step by 0.05 s, or change playback speed. The radar coverage toggle in the view tools shows every sentry's sector and elevation limits, with a line to each contact it holds — cool while it only watches, warm once it commits. Analysis displays telemetry for the selected vehicle. The browser pauses a live run when its tab becomes hidden.
6. **Save project** stores the scenario in browser local storage and the latest recording in IndexedDB. **Replay** captures the current run and allows scrubbing. Scenarios and recordings can be exported/imported as JSON; CSV contains one telemetry row per vehicle per simulated second. Browser storage is local to the browser profile and site origin.

## Tactical air base example

**Scenarios → Tactical air base** opens a larger fictional field, **서해 전술비행단 (가상)**. It is built from the general form of a single-runway tactical air base rather than from any survey or photograph: one 2,700 m runway on a 020° axis, taxiways paralleling it end to end, crossovers and turn pads, two combed rows of aircraft shelters on their own stubs, a maintenance apron with a hangar line, a support area with tower and barracks, fuel and munitions storage, twenty sentry charging pods, and a perimeter road. Outside that road a generated woodland belt wraps the base on every side, clipped to clear the built field and to stop at the edge of the modelled ground. 185 map objects in all, about 4,700 trees among them.

The layout is authored in runway-local metres in `src/airbase.ts` — `u` along the runway, `v` across it — and rotated onto the base axis, so every piece stays aligned if you change the heading. Dimensions, headings, and heights are illustrative choices, not measurements, and the field does not reconstruct a real installation.

The scenario runs three jet departures from the south threshold while twenty sentries rotate between a patrol ring and their pods, form up before the roll, and meet a guided wave of ramming drones. Nothing about the outcome is authored: the engagement is decided by where the sentries are, what their radar reaches, and whether a lead intercept exists. Everything is editable afterwards — objects move with the translation handles, stations and envelopes open in the inspector, and the wave re-rolls from the Threat panel.

Runway end markings follow the object's rotation, so a runway you rotate repaints itself in the 01–36 convention. The ground boundary and access roads are drawn from the extent of the built field, with woodland treated as landscape outside it, and the default camera distances, zoom limits, and shadow extent scale with the scene, so small and large fields both frame correctly.

Every grove in the belt is an ordinary map object. Select one to move, resize, or delete it like any other, or raise its height to thicken the canopy.

## Fictional image to 3D

Switch to **Map setup** and choose **Image to 3D**. The bundled coastal airport is newly generated artwork with no reference photograph. Its demo title, **서산공군기지(가상)**, labels a fictional scene; the layout is not a reconstruction of a real installation.

Select an outline in the image or object list, then change its label, type, dimensions, rotation, and illustrative height. **Draw outline** adds a rectangle with two clicks. **Build 3D scene** replaces the current project with an editable coastal scene and one educational takeoff; **Undo** restores the previous project. Reopening the image editor preserves existing flights, routes, weather, and scripted events. The map icon beside Undo toggles the reference image under the 3D geometry.

This is assisted tracing and extrusion, not photogrammetry or automatic height inference. The 3,000 × 2,000 m canvas and all heights are artistic choices. Generated roofs and shadows remain printed on the reference image after an object moves; hide the reference layer for a clean geometry view. The editor uses the bundled fictional concept and does not accept image uploads.

Outlines become ordinary map objects, so the existing inspector, translation handles, save/reload, JSON import/export, and undo/redo work as before. Schema version 1 adds an optional `referenceMap` with an allowlisted built-in image ID and visibility flag. Older scenarios remain supported. The image is in `public/maps/fictional-coast.png`; its exact generation prompt is in `public/maps/generation-prompt.txt`.

## Models and limits

The base, the sentries, and the hostile drones are fictional. The departures are not: they fly published F-35A figures, with the unpublished ground roll derived from thrust to weight and labelled as such. The supplied jet artwork is a generic airframe and does not establish aircraft performance data. Flight uses a fixed 0.05 s step, direct waypoint motion, limited climb, and educational wind drift. Every airframe accelerates and brakes at its own figure rather than a shared constant; routes are flown through rather than braked into, but a drone holding a point brakes into it under its own acceleration instead of snapping to a halt, and holding a point in wind costs the airspeed needed to cancel the drift. Contact between two movers is swept over each step rather than sampled at its end, so a fast pass cannot jump an engagement radius. Energy is the integral of the user-defined airspeed/power curve. Available capacity decreases by 0.8% per degree below 20°C, with a 55% floor; this is an adjustable-model assumption, not a measured battery specification. Depletion ends the modeled flight at its current location.

Observations are synthetic, seeded noisy positions with configurable loss and delay. Rain and visibility increase loss through a toy model. They are not radar waveforms.

The sentry envelope borrows published TI AWR2944P figures because they are a concrete, honest set of numbers to reason about coverage with. That is the whole extent of the borrowing: detection is a cone-and-range test against those figures, and everything after a contact — which drone goes, the crossing-point geometry, the modelled outcome — is a teaching abstraction with no basis in how any real system behaves. There is no guidance, fire control, waveform, device interface, or targeting firmware here, and that radar is an automotive sensing module, not a counter-drone product. Encounter outcomes resolve from the modelled geometry, and authored timeline events remain available alongside it. The separate hardware report is available from **Hardware lab**.

## Data and verification

`ScenarioDocument` and `RunRecord` use schema version 1. Runs include a scenario snapshot and simulator version. Replay uses recorded 0.5 s frames with visual interpolation; telemetry is sampled each second. Pause and playback rates do not change simulation steps. Identical scenario and seed reproduce results within this simulator version. Invalid imports are rejected before replacing the open scenario.

`npm run verify` checks representative outcomes, conflict handling, takeoff failures, energy accounting, data validation, repeatability, and the ten-minute performance case. For the engagement it checks the envelope against each published sensor figure including the velocity ceiling, that the fleet patrols and charges and then takes station on cue, that the ring carries enough drones to close it and that the split matches the battery duty cycle, that a wave is guided onto the departure rather than flown on a fixed course, the crossing-point geometry — the abeam case, the straight-overhead case that resolves to a vertical dash, a target already past, a dash too far to make — the swept contact test that stops a fast pass slipping between two samples, that the runway centreline sits inside each sentry's envelope and that each is agile enough to cross its own bubble, that the default wave is mostly but not entirely held with every takedown inside engagement range, that a rolled wave is reproducible from its plan, and that a faster saturating wave gets through. It writes its result to the sibling outputs directory. Browser rendering, persistence, downloads, and editing are separately checked through the visible UI.

The application targets desktop Chrome and Edge with WebGL2. All calculations and user data remain in the browser. The source uses TypeScript, Vite, and Three.js; it has no server API or environment secrets. Fonts load from Google Fonts with a system-font fallback. Hosting access is managed by your chosen provider.
