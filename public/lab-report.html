Indoor sensing.
Independent FPGA learning.

A practical comparison of five development boards for a stationary, non-weapon laboratory. Start small, measure the actual workload, and keep the sensor and FPGA experiments independent.

Recommended starting point

Begin with an IWRL6432BOOST for indoor presence and point-cloud demonstrations and a PYNQ-Z2 basic kit for Python, digital-logic, and recorded-data exercises. Compatibility and accessory decisions

Keep the first two exercises separate

Run a vendor indoor sensing demo on the computer. Use the FPGA board for its own examples and synthetic or recorded datasets. No documented, ready-to-use radar-to-Zynq integration was established for this report; a matching connector or Ethernet port does not establish electrical, protocol, driver, or software compatibility.

TI documents DCA1000 connectivity for both listed sensor evaluation boards. The IWRL6432 family uses a different SDK and raw-data interface from IWR6843, so follow the exact board revision's supported capture workflow. IWRL6432BOOST documentation · IWR6843ISK documentation.

Allow for the entire bench setup

  • Appropriate vendor-specified power supplies, USB data cables, Ethernet, spare microSD, and a card reader. The boards do not all use the same power adapter.
  • Stable tabletop supports, an ESD mat, and a small power meter. Avoid counting accessories already included in the PYNQ basic kit twice.
  • For optional raw capture: a supported host OS/tool version, suitable network adapter and storage, and the correct TI cable/adapter set. Check kit contents before purchasing extras.
  • If source-level IWR6843 debugging is needed, price the optional MMWAVEICBOOST separately before buying; it is not included in this board subtotal.

PYNQ-Z2 manual documents its supply and shared pins. Digilent documents board-revision changes to Ethernet and flash devices. Tool/OS compatibility must be checked against the chosen release; a web browser running the simulator does not establish support for vendor hardware tools.

Turn specifications into evidence

  1. Record the configuration. Keep board revision, firmware, tool release, supply, and indoor test conditions with each result.
  2. Measure the board. Log actual wall-input power, repeatability, data delivery rate, and dropped records during a vendor demonstration.
  3. Benchmark the learning workload. Run a fixed offline dataset on each FPGA platform; record completion time, memory use, and programmable-logic utilization. Do not infer performance from clock frequency alone.
  4. Revisit purchases only after a limitation appears. Add raw capture or a larger-memory development board when the recorded exercise demonstrates a need.
